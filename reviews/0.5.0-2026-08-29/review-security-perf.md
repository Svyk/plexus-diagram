# Plexus Diagram v0.5.0 — Security & Performance Review

Scope: security and performance only, against `reviews/0.5.0-2026-08-29/diff.txt`, with `src/canvas.js` (pointer capture, connect listeners, color CSS) and `src/feature.js` (nested attach) read in full for context. `src/library.js` is untouched in this diff and was not in scope.

## Nested-board navigation leaks a full session + live pull-watch per diagram visited

**File:** src/feature.js:247-281 (also src/session.js:36-52, src/session.js:141-153, src/view.js:96-102)
**Severity:** critical
**Type:** performance
**What is wrong:** `attachViewSession` (src/feature.js:247) swaps the shared canvas/wrapper's view from the parent session onto the child session (`parent.removeView(view)` at line 266, `child.addView(view)` at line 276) and calls `child.startWatch()` (line 258), but it never calls `parent.stopWatch()`. The parent `NativeDiagramSession` stays in the module-level `sessions` map (src/session.js:155) forever — `getOrCreateSession` only clears it via explicit `disposeSession` (extension unload or "Restore native diagram"), and `pruneDetachedViews` (src/session.js:141) only disposes sessions whose *views* have a disconnected DOM root. Here the wrapper/canvas stay connected (they're reused by the child), and the parent session now has zero views, so `pruneDetachedViews` has nothing to iterate and the session is never reaped. Its `this.unwatch` (a live `roamAlphaAPI.data.addPullWatch` subscription registered in `DiagramAdapter.watchExternal`, src/adapter.js:81-94) keeps running indefinitely. This is exactly the "in-place nested boards" feature from the 0.5.0 changelog — because opening a nested diagram no longer calls `openBlock`/changes the hash, the old page-navigation path that used to tear down and remount (and thus dispose stale sessions) no longer runs.
**Attack vector / Impact:** Not attacker-triggered, but any normal user drilling into N distinct nested diagrams over a session accumulates N permanently-live pull-watch subscriptions and N retained `DiagramModel` objects (full node/edge/section maps), none of which is ever released short of a full extension reload. Every one of those pull watches is re-evaluated by Roam on *every* subsequent datalog transaction anywhere in the graph (not just diagram edits), so this is an unbounded, monotonically growing tax on all future writes — worse the longer a session runs and the more nested boards a user has opened, with no natural cap.
**What needs to change:** When `attachViewSession` moves a session's last view away, check whether the vacated parent session has zero remaining views and, if so, `stopWatch()` it (and optionally drop it from `sessions` after some grace period, re-hydrating via `getOrCreateSession` on the way back through a crumb). At minimum, `attachViewSession` should call `parent.stopWatch()` when `parent.views.size === 0` after `removeView`, and `child.startWatch()` should be balanced by resuming/re-arming the parent's watch if the user pops back out via a crumb (the crumb path already re-attaches the ancestor session, so a paired `startWatch()`/`stopWatch()` bracket around "session is the one currently shown" would close the leak without changing the crumb/back-stack semantics.

## Extra sequential Roam-write round trip per node/section, run on every nested/crumb hop

**File:** src/metadata.js:257-306 (color prop sync), src/view.js:43-44,55-56 (persistLayout before every nested/crumb transition)
**Severity:** warning
**Type:** performance
**What is wrong:** `patchDiagramBlock` already syncs each node/section's `pos::`/`size::`(/`title::`) as separate sequentially-`await`ed `syncPropChild` calls per row (src/metadata.js:265-267, 299-302); 0.5.0 adds one more sequential `await syncPropChild(...)` per node and per section for `color::`. `MetadataStore.set` does short-circuit on an unchanged serialization (src/metadata.js:360), so this only fires when the in-memory layout actually differs from what's stored — but `view.js`'s `onPersist` handler now calls `current.persistLayout()` before *every* `openNested` and every `openCrumb` (src/view.js:44, 56), i.e. on every dive-in/pop-out of a nested board, not just on explicit saves. For a diagram with many cards this turns "open a nested card" into an O(nodes + edges + sections) chain of sequentially-awaited Roam calls whenever there is any unsaved layout delta (drag, resize, or a color change), and the color addition increases that per-row round-trip count by 33–50%.
**Attack vector / Impact:** No security impact; this is a latency/perf regression that scales with diagram size and nesting depth. A large diagram (dozens of cards/sections) with any pending layout change will visibly stall the "double-click to open nested" / crumb-pop interaction while the sequential writes flush, and it will do so every time the user moves between boards rather than only on an explicit save.
**What needs to change:** Batch the per-row prop writes (e.g. `Promise.all` across the independent `syncPropChild` calls for a given row, and across rows where Roam's API allows concurrent writes) instead of awaiting each one serially, or debounce/skip the pre-navigation `persistLayout()` call when nothing but the viewport changed (viewport is already persisted separately via `persistViewport`/`setViewport`, so the nested/crumb handlers arguably don't need to force a synchronous full-layout flush before navigating at all).

## Connect-arm stays globally armed with no idle bound

**File:** src/canvas.js:1135-1152
**Severity:** suggestion
**Type:** performance
**What is wrong:** `armConnect` (src/canvas.js:1140) registers a capture-phase `pointermove` listener on `document` (not scoped to the canvas root) that persists for as long as `connectArm` is set. Cleanup paths (`clearConnectArm` on Escape, tool switch, `attachSession`, `completeConnect`'s `finally`, and `dispose()`) all look correct and I did not find a path that leaves it registered after the canvas is torn down or the tool changes — so this is not a leak in the strict sense. However, there is no idle/time bound: if a user click-arms Connect (single click on a card with the Connect tool, src/canvas.js:1781) and then simply clicks elsewhere in the page chrome, switches tabs, or walks away without pressing Escape or completing a second click, the global capture-phase listener keeps running `screenToWorld` + `setTempEdge` DOM work on every mouse movement anywhere on the page indefinitely.
**Attack vector / Impact:** Not attacker-controlled; purely a self-inflicted, easy-to-hit UX/perf edge case (single accidental click on Connect + card arms it with no visual timeout), and the cost per move is small, but it's unbounded in *duration* rather than *count*, which is worth tightening given it listens at `document` scope rather than the canvas root.
**What needs to change:** Either scope the listener to `root` instead of `document`, or clear the arm automatically on `blur`/`visibilitychange`/clicking outside the canvas, so a forgotten armed state can't keep a page-wide capture listener alive across tab switches.

## Checked, no issue found: color values and title/label text never reach `innerHTML`/`style` unsanitized

Per the brief's explicit ask, I traced every path where a user-writable value (`node.color`, `section.color`, section title, edge label) reaches the DOM:
- `colorHex()` (src/canvas.js:358-361) is the only consumer of `node.color`/`section.color` for styling (`paintCardColor` src/canvas.js:1411, `paintSectionColor` src/canvas.js:810). It does an exact-match lookup against the fixed `COLOR_SWATCHES` table and returns `""` for anything else, so an out-of-band or hand-edited `color:: <anything>` value in the metadata block can never inject into `style.background`/`color-mix(...)` — it just gets ignored. This holds even though `metadata.js` round-trips arbitrary `color::` strings verbatim (src/metadata.js:169, 181, 267, 302) into/out of Roam blocks.
- Section titles and edge labels are always assigned via `.textContent` (src/canvas.js:873, 917, 1083) or as `title`/attribute values (src/canvas.js:1063, 1070, 1085), never concatenated into `innerHTML` or `cssText`. Every `innerHTML` write in `src/canvas.js` (lines 504, 675, 944, 1035, 1132, 1218, 1378) either clears a node (`= ""`) or assigns a static, non-interpolated markup string (`defs.innerHTML` at line 944) — none interpolate `title`, `label`, or `color`.

No action needed here; listed for completeness since it was explicitly called out in the review brief.
